# Memory Audit Architecture

> 一种用于 AI Agent 持久记忆管理的架构设计。

---

## 1. 问题

AI Agent 的记忆会随时间退化。

每次会话都会产生新的信息——用户偏好、环境事实、操作经验。这些信息被写入持久存储，跨会话保留。但没有机制来清理它们。

结果是可预见的：

- **冗余**：同一信息以不同形式存在于多个层级
- **过时**：环境变化后，旧条目不再准确
- **膨胀**：记忆容量逐渐耗尽，压缩新信息的空间
- **混乱**：条目分类错误，偏好与流程混杂

这不是存储空间的问题，而是信息质量的问题。一个充满过时、冗余条目的记忆系统，比没有记忆更危险——Agent 会基于错误的前提做出决策。

Memory Audit 是一种主动管理机制：通过定期审查、分级响应、反馈追踪，维持记忆的准确性和可用性。

## 2. 核心理念

### 2.1 主动优于被动

> 不要等到记忆溢出才清理。

定期审计防止问题积累，而非响应危机。就像定期体检比急诊更有效——早期发现的问题更容易修复，成本更低。

**实践**：三级审计周期（每日/每周/每月），从轻量扫描到深度审查。

### 2.2 报告即历史

> 审计报告本身就是决策记录。

不需要单独的决策存储。每份报告包含当期的审查结果、发现的问题、采取的行动、用户的决策。历史就写在报告里。

**实践**：反馈状态文件只追踪活跃项（pending/deferred），已完成的决策在报告中归档后删除。

### 2.3 渐进式响应

> 不是每个问题都需要人类介入。

严重度决定响应路径。格式问题自动修复，分类错误需要人工判断。这样用户只关注真正重要的决策，不被琐事打扰。

**实践**：五级严重度（trivial → critical），从自动修复到立即告警。

### 2.4 最小化用户操作

> 一次回复处理所有待决项。

用户不应该逐条审批。提供批量操作：「全部同意」「全部忽略」「推迟」，或者一次自定义指令处理多个条目。

**实践**：交互协议支持批量操作，不回复则保持 pending 状态，不推送提醒。

## 3. 概念模型

### 3.1 记忆模型

审计系统需要理解被审计的对象。AI Agent 的持久记忆通常按稳定性和用途分层：

```
┌─────────────────────────────────────────────────────┐
│  Layer 1: Config                                     │
│  平台凭据、服务配置、功能开关                          │
│  变化频率：极少                                       │
├─────────────────────────────────────────────────────┤
│  Layer 2: Profile                                    │
│  交互偏好、沟通风格、用户习惯                          │
│  变化频率：偶尔                                       │
├─────────────────────────────────────────────────────┤
│  Layer 3: Memory                                     │
│  一行索引，指向 Skills 中的详细内容                     │
│  变化频率：中等                                       │
├─────────────────────────────────────────────────────┤
│  Layer 4: Skills                                     │
│  完整流程、详细手册、深度知识                          │
│  变化频率：中等                                       │
├─────────────────────────────────────────────────────┤
│  Layer 5: Session                                    │
│  当前对话上下文、临时状态                              │
│  变化频率：极高（会话级）                              │
└─────────────────────────────────────────────────────┘
```

**设计意图**：

- **Progressive Disclosure**：Memory 只存一行索引，Skills 存完整内容。这样 Agent 的活跃上下文保持精简，需要时再加载详情。
- **Separation of Concerns**：配置、偏好、知识、上下文各归其位，不互相污染。

**存储决策**：

```
信息 X 需要持久化
    │
    ├─ 平台配置/凭据？     → Config (Layer 1)
    ├─ 影响交互方式的偏好？ → Profile (Layer 2)
    ├─ 短事实/行为约束？   → Memory (Layer 3)
    ├─ 可复用流程/深度知识？→ Skills (Layer 4)
    └─ 仅当前会话相关？    → Session (Layer 5)，不持久化
```

> 五层是参考模型，不是硬性要求。简单 Agent 可能只需要三层（Config / Memory / Session）。审计系统应适配你的实际层级结构。

### 3.2 审计周期

三级审计覆盖不同深度：

```
┌─────────────────────────────────────────────────────┐
│  每日审计                                            │
│  轻量扫描：容量检查、重复检测、格式问题                 │
│  自动处理 trivial/minor，记录 moderate/major          │
├─────────────────────────────────────────────────────┤
│  每周审计                                            │
│  中等审查：汇总 7 天发现、独立深度检查                   │
│  处理反馈、执行清理、生成周报                          │
├─────────────────────────────────────────────────────┤
│  每月审计                                            │
│  深度审查：跨周趋势、健康度评分、长期分析                │
│  汇总月度数据、追踪遗留问题                            │
└─────────────────────────────────────────────────────┘
```

**为什么是三级？**

- 单级审计要么太频繁（深度审计每天跑太重），要么太稀疏（轻量审计每月跑太慢）
- 三级形成互补：每日抓显而易见的问题，每周处理需要判断的问题，每月看趋势
- 每级独立可选——你可以只做每日（轻量）或只做每月（深度）

**设计意图**：

- 每日审计快速、自动、无用户交互
- 每周审计处理用户反馈，是主要的交互节点
- 每月审计提供全局视角，不执行清理

## 4. 关键机制

### 4.1 严重度分级

问题按影响程度分为五级：

| 级别 | 定义 | 响应 |
|------|------|------|
| **trivial** | 仅影响可读性（格式、标点） | 自动修复，不记录 |
| **minor** | 改善性修改，不改变含义 | 自动修复，记录到报告 |
| **moderate** | 需要移动或重写条目 | 报告，等待用户批准 |
| **major** | 需要删除或大幅重写 | 报告，等待用户批准 |
| **critical** | 涉及安全或数据完整性 | 立即告警 + 自动修复 |

**设计意图**：

- trivial/minor 占大多数，自动处理节省时间
- moderate/major 需要判断，交给用户
- critical 极少但紧急，立即处理

### 4.2 反馈生命周期

审计发现的问题进入反馈追踪系统，经历完整的生命周期：

```
    ┌──────────┐
    │  审计    │
    │  发现    │
    └────┬─────┘
         │
         ▼
    ┌──────────┐
    │  pending │ ← 新问题进入
    └────┬─────┘
         │
    ┌────┴────┐
    ▼         ▼
┌────────┐ ┌──────────┐
│decided │ │ deferred │
│(已决策) │ │ (推迟)   │
└────┬───┘ └────┬─────┘
     │          │
     ▼          ▼
┌──────────┐ ┌──────────┐
│ 下一份   │ │ 保持直到  │
│ 报告归档 │ │ 决策/超时 │
└──────────┘ └──────────┘
```

**状态说明**：

- **pending**：新发现的问题，等待用户处理
- **decided**：用户已做出决策（批准/忽略）
- **deferred**：用户推迟，稍后处理

**清理规则**：

- decided 项在下一份报告中展示后删除
- 任何项超过 60 天自动删除（兜底机制）
- deferred 项保持直到用户决策或 60 天

**为什么用文件而非数据库？**

- 人类可读：直接打开 feedback.json 查看状态
- 可版本控制：git diff 追踪变更
- 无基础设施依赖：不需要运行数据库服务
- 简单够用：反馈条目通常在个位数到低两位数

**设计意图**：

- 报告本身就是历史，不需要额外存储
- 60 天超时防止僵尸条目积累
- 用户不回复时保持 pending，不推送提醒

### 4.3 智能清理

文件清理根据待决状态决定：

```
无 pending 且无 moderate/major 问题
    → 自动删除过期文件

仅有 trivial/minor 问题
    → 自动删除

有 moderate/major pending
    → 等用户确认后再删除
```

**设计意图**：

- 无待决项时，清理是安全的，自动执行
- 有待决项时，保留文件供用户参考
- 避免在用户还在思考时删除证据

### 4.4 配置结构

审计系统通过配置文件控制行为。推荐使用 JSON 格式（`config.json`），包含以下部分：

| 字段 | 说明 | 示例 |
|------|------|------|
| `data_dir` | 数据存储根目录 | `$DATA_DIR/memory-audit` |
| `retention.daily_reports` | 每日报告保留天数 | `14` |
| `retention.daily_backups` | 每日备份保留天数 | `14` |
| `retention.weekly_reports` | 周报告保留天数（-1 = 永久） | `-1` |
| `retention.monthly_reports` | 月报告保留天数（-1 = 永久） | `-1` |
| `retention.feedback_timeout_days` | 反馈条目超时天数 | `60` |
| `audit_schedule.daily` | 每日审计 cron 表达式 | `0 9 * * *` |
| `audit_schedule.weekly` | 每周审计 cron 表达式 | `0 10 * * 1` |
| `audit_schedule.monthly` | 每月审计 cron 表达式 | `0 10 1 * *` |
| `severity.auto_fix` | 自动修复的严重度级别 | `["trivial", "minor"]` |
| `severity.require_approval` | 需要用户批准的级别 | `["moderate", "major"]` |
| `severity.immediate_alert` | 立即告警的级别 | `["critical"]` |
| `notification.daily` | 每日审计通知目标 | `"<your-notification-target>"` |
| `notification.weekly` | 每周审计通知目标 | `"<your-notification-target>"` |
| `notification.monthly` | 每月审计通知目标 | `"<your-notification-target>"` |

`retention` 对应 4.3 的清理策略，`severity` 对应 4.1 的严重度分级，`audit_schedule` 对应 3.2 的审计周期。`notification` 配置各审计级别的通知渠道（邮件、IM、webhook 等），格式取决于你的通知系统。

## 5. 实践指南

### 5.1 如何应用

**第一步：定义你的记忆层级**

不一定需要五层。关键原则：

- 每层有明确的职责边界（什么信息属于哪层）
- 每层有容量限制（防止无限膨胀）
- 层级之间有清晰的流转规则（什么时候从 Memory 升级到 Skills）

**第二步：建立审计机制**

根据你的调度能力选择频率：

| 频率 | 适合场景 |
|------|----------|
| 每日 | 记忆频繁更新的 Agent |
| 每周 | 中等使用频率 |
| 每月 | 低频或辅助审计 |

**第三步：实现反馈循环**

使用反馈状态文件（推荐 JSON 格式）跟踪活跃项目。报告保留历史，状态文件只存储当前。

信封结构：
- `version`：Schema 版本（整数，如 `1`）
- `updated`：最后修改时间（ISO-8601）
- `items`：反馈条目数组

每条核心字段：
- `id`：唯一标识
- `issue`：问题描述
- `severity`：严重度级别（trivial / minor / moderate / major / critical）
- `action`：建议操作
- `status`：当前状态（pending / decided / deferred）
- `created`：发现时间（ISO-8601）
- `decision`：用户决策文本（decided/deferred 时填写）
- `decided`：决策时间（decided 时填写）

**第四步：配置清理策略**

设定保留期限：
- 每日报告：7-30 天
- 每周/月报告：永久
- 反馈超时：30-90 天

### 5.2 适配建议

| 你的场景 | 建议 |
|----------|------|
| 单 Agent，文件存储 | 直接采用本架构 |
| 多 Agent，共享记忆 | 添加共享知识层，审计时合并视图 |
| 数据库存储 | 反馈状态用数据库表，报告用结构化记录 |
| 无定时调度 | 手动触发审计，或在会话开始时检查 |
| 无通知渠道 | 审计结果写入日志，会话时展示 |

### 5.3 常见陷阱

**审计判断标准不明确**

最容易犯的错误是把条目放错层级。明确分类规则：

- Profile 只放交互偏好（沟通风格、语言、审批模式）
- Memory 只放短事实和行为约束（一行索引）
- Skills 放完整流程和深度知识

如果一条信息既有偏好又有流程，拆成两部分分别存放。

**审计执行者的上下文限制**

如果审计由 AI Agent 自身执行（而非独立脚本），需要注意一个根本性矛盾：审计者无法同时拥有被审计记忆的完整视图和独立判断力。

- Agent 的工具可能无法读取自身记忆的全部内容
- Agent 的判断可能受自身记忆中的偏见影响
- 解决方案：使用预执行脚本将当前状态注入审计上下文，或定期用独立脚本交叉验证

> 以 Hermes Agent 为例：cron 审计任务以 `skip_memory` 模式运行，无法直接调用 memory 工具。通过预执行脚本（pre-exec script）将当前记忆状态序列化后注入上下文，绕过这一限制。

**反馈超时设置过短**

60 天是推荐值。如果你的用户不经常在线，考虑延长到 90 天或更长。超时删除是兜底机制，不应频繁触发。

**备份与清理的时机**

清理前必须备份。建议流程：
1. 审计前创建备份
2. 执行审计，生成报告
3. 自动处理 trivial/minor
4. 报告 moderate/major 给用户
5. 用户确认后再删除备份

### 5.4 常见问题

**Q: 审计会不会很慢？**

A: 每日审计只检查明显问题（容量、重复），通常几秒完成。深度审查留给每周/月。

**Q: 用户不回复怎么办？**

A: pending 项保持，不推送提醒。超过 60 天自动清理。用户永远可以主动查看待决项。

**Q: 如何处理误删？**

A: 每次审计前备份。周/月报告永久保留，可从中恢复决策记录。

**Q: 可以只做部分审计吗？**

A: 可以。三级是建议，你可以只做每日（轻量）或只做每月（深度）。

## 附录：设计决策记录

| 决策 | 考虑的替代方案 | 选择理由 |
|------|----------------|----------|
| 报告即历史 | 独立决策数据库 | 更简单，报告已包含完整上下文 |
| 文件系统存储 | 数据库/向量存储 | 人类可读、可版本控制、无基础设施依赖 |
| 手动分类 | 自动嵌入路由 | 确定性、可解释、无模型依赖 |
| 固定保留期 | 动态调整 | 简单可预测，不增加复杂度 |
| 60 天超时 | 无超时 | 防止僵尸条目，强制周期性决策 |
| 三级审计 | 单级或多级 | 三级互补，每级独立可选 |
| 反馈追踪在审计侧 | 反馈追踪在记忆侧 | 审计系统负责质量，记忆系统负责存储 |
