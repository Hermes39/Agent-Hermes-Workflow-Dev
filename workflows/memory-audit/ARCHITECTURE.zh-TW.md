# Memory Audit Architecture

> 一種用於 AI Agent 持久記憶管理的架構設計。

---

## 1. 問題

AI Agent 的記憶會隨時間退化。

每次會話都會產生新的資訊——使用者偏好、環境事實、操作經驗。這些資訊被寫入持久儲存，跨會話保留。但沒有機制來清理它們。

結果是可預見的：

- **冗餘**：同一資訊以不同形式存在於多個層級
- **過時**：環境變化後，舊條目不再準確
- **膨脹**：記憶容量逐漸耗盡，壓縮新資訊的空間
- **混亂**：條目分類錯誤，偏好與流程混雜

這不是儲存空間的問題，而是資訊品質的問題。一個充滿過時、冗餘條目的記憶系統，比沒有記憶更危險——Agent 會基於錯誤的前提做出決策。

Memory Audit 是一種主動管理機制：透過定期審查、分級回應、反饋追蹤，維持記憶的準確性和可用性。

## 2. 核心理念

### 2.1 主動優於被動

> 不要等到記憶溢出才清理。

定期審計防止問題累積，而非回應危機。就像定期體檢比急診更有效——早期發現的問題更容易修復，成本更低。

**實踐**：三級審計週期（每日/每週/每月），從輕量掃描到深度審查。

### 2.2 報告即歷史

> 審計報告本身就是決策記錄。

不需要單獨的決策儲存。每份報告包含當期的審查結果、發現的問題、採取的行動、使用者的決策。歷史就寫在報告裡。

**實踐**：反饋狀態檔案只追蹤活躍項（pending/deferred），已完成的決策在報告中歸檔後刪除。

### 2.3 漸進式回應

> 不是每個問題都需要人類介入。

嚴重度決定回應路徑。格式問題自動修復，分類錯誤需要人工判斷。這樣使用者只關注真正重要的決策，不被瑣事打擾。

**實踐**：五級嚴重度（trivial → critical），從自動修復到立即告警。

### 2.4 最小化使用者操作

> 一次回覆處理所有待決項。

使用者不應該逐條審批。提供批次操作：「全部同意」「全部忽略」「推遲」，或者一次自訂指令處理多個條目。

**實踐**：互動協定支援批次操作，不回覆則保持 pending 狀態，不推送提醒。

## 3. 概念模型

### 3.1 記憶模型

審計系統需要理解被審計的物件。AI Agent 的持久記憶通常按穩定性和用途分層：

```
┌─────────────────────────────────────────────────────┐
│  Layer 1: Config                                     │
│  平台憑證、服務配置、功能開關                          │
│  變化頻率：極少                                       │
├─────────────────────────────────────────────────────┤
│  Layer 2: Profile                                    │
│  互動偏好、溝通風格、使用者習慣                        │
│  變化頻率：偶爾                                       │
├─────────────────────────────────────────────────────┤
│  Layer 3: Memory                                     │
│  一行索引，指向 Skills 中的詳細內容                     │
│  變化頻率：中等                                       │
├─────────────────────────────────────────────────────┤
│  Layer 4: Skills                                     │
│  完整流程、詳細手冊、深度知識                          │
│  變化頻率：中等                                       │
├─────────────────────────────────────────────────────┤
│  Layer 5: Session                                    │
│  當前對話上下文、暫時狀態                              │
│  變化頻率：極高（會話級）                              │
└─────────────────────────────────────────────────────┘
```

**設計意圖**：

- **Progressive Disclosure**：Memory 只存一行索引，Skills 存完整內容。這樣 Agent 的活躍上下文保持精簡，需要時再載入詳情。
- **Separation of Concerns**：配置、偏好、知識、上下文各歸其位，不互相污染。

**儲存決策**：

```
資訊 X 需要持久化
    │
    ├─ 平台配置/憑證？     → Config (Layer 1)
    ├─ 影響互動方式的偏好？ → Profile (Layer 2)
    ├─ 短事實/行為約束？   → Memory (Layer 3)
    ├─ 可複用流程/深度知識？→ Skills (Layer 4)
    └─ 僅當前會話相關？    → Session (Layer 5)，不持久化
```

> 五層是參考模型，不是硬性要求。簡單 Agent 可能只需要三層（Config / Memory / Session）。審計系統應適配你的實際層級結構。

### 3.2 審計週期

三級審計覆蓋不同深度：

```
┌─────────────────────────────────────────────────────┐
│  每日審計                                            │
│  輕量掃描：容量檢查、重複偵測、格式問題                 │
│  自動處理 trivial/minor，記錄 moderate/major          │
├─────────────────────────────────────────────────────┤
│  每週審計                                            │
│  中等審查：彙整 7 天發現、獨立深度檢查                   │
│  處理反饋、執行清理、生成週報                          │
├─────────────────────────────────────────────────────┤
│  每月審計                                            │
│  深度審查：跨週趨勢、健康度評分、長期分析                │
│  彙整月度資料、追蹤遺留問題                            │
└─────────────────────────────────────────────────────┘
```

**為什麼是三級？**

- 單級審計要麼太頻繁（深度審計每天跑太重），要麼太稀疏（輕量審計每月跑太慢）
- 三級形成互補：每日抓顯而易見的問題，每週處理需要判斷的問題，每月看趨勢
- 每級獨立可選——你可以只做每日（輕量）或只做每月（深度）

**設計意圖**：

- 每日審計快速、自動、無使用者互動
- 每週審計處理使用者反饋，是主要的互動節點
- 每月審計提供全域視角，不執行清理

## 4. 關鍵機制

### 4.1 嚴重度分級

問題按影響程度分為五級：

| 級別 | 定義 | 回應 |
|------|------|------|
| **trivial** | 僅影響可讀性（格式、標點） | 自動修復，不記錄 |
| **minor** | 改善性修改，不改變含義 | 自動修復，記錄到報告 |
| **moderate** | 需要移動或重寫條目 | 報告，等待使用者批准 |
| **major** | 需要刪除或大幅重寫 | 報告，等待使用者批准 |
| **critical** | 涉及安全或資料完整性 | 立即告警 + 自動修復 |

**設計意圖**：

- trivial/minor 佔大多數，自動處理節省時間
- moderate/major 需要判斷，交給使用者
- critical 極少但緊急，立即處理

### 4.2 反饋生命週期

審計發現的問題進入反饋追蹤系統，經歷完整的生命週期：

```
    ┌──────────┐
    │  審計    │
    │  發現    │
    └────┬─────┘
         │
         ▼
    ┌──────────┐
    │  pending │ ← 新問題進入
    └────┬─────┘
         │
    ┌────┴────┐
    ▼         ▼
┌────────┐ ┌──────────┐
│decided │ │ deferred │
│(已決策) │ │ (推遲)   │
└────┬───┘ └────┬─────┘
     │          │
     ▼          ▼
┌──────────┐ ┌──────────┐
│ 下一份   │ │ 保持直到  │
│ 報告歸檔 │ │ 決策/逾時 │
└──────────┘ └──────────┘
```

**狀態說明**：

- **pending**：新發現的問題，等待使用者處理
- **decided**：使用者已做出決策（批准/忽略）
- **deferred**：使用者推遲，稍後處理

**清理規則**：

- decided 項在下一份報告中展示後刪除
- 任何項超過 60 天自動刪除（兜底機制）
- deferred 項保持直到使用者決策或 60 天

**為什麼用檔案而非資料庫？**

- 人類可讀：直接開啟 feedback.json 查看狀態
- 可版本控制：git diff 追蹤變更
- 無基礎設施依賴：不需要執行資料庫服務
- 簡單夠用：反饋條目通常在個位數到低兩位數

**設計意圖**：

- 報告本身就是歷史，不需要額外儲存
- 60 天逾時防止殭屍條目累積
- 使用者不回覆時保持 pending，不推送提醒

### 4.3 智慧清理

檔案清理根據待決狀態決定：

```
無 pending 且無 moderate/major 問題
    → 自動刪除過期檔案

僅有 trivial/minor 問題
    → 自動刪除

有 moderate/major pending
    → 等使用者確認後再刪除
```

**設計意圖**：

- 無待決項時，清理是安全的，自動執行
- 有待決項時，保留檔案供使用者參考
- 避免在使用者還在思考時刪除證據

### 4.4 配置結構

審計系統透過配置檔案控制行為。推薦使用 JSON 格式（`config.json`），包含以下部分：

| 欄位 | 說明 | 範例 |
|------|------|------|
| `data_dir` | 資料儲存根目錄 | `$DATA_DIR/memory-audit` |
| `retention.daily_reports` | 每日報告保留天數 | `14` |
| `retention.daily_backups` | 每日備份保留天數 | `14` |
| `retention.weekly_reports` | 週報告保留天數（-1 = 永久） | `-1` |
| `retention.monthly_reports` | 月報告保留天數（-1 = 永久） | `-1` |
| `retention.feedback_timeout_days` | 反饋條目逾時天數 | `60` |
| `audit_schedule.daily` | 每日審計 cron 表達式 | `0 9 * * *` |
| `audit_schedule.weekly` | 每週審計 cron 表達式 | `0 10 * * 1` |
| `audit_schedule.monthly` | 每月審計 cron 表達式 | `0 10 1 * *` |
| `severity.auto_fix` | 自動修復的嚴重度級別 | `["trivial", "minor"]` |
| `severity.require_approval` | 需要使用者批准的級別 | `["moderate", "major"]` |
| `severity.immediate_alert` | 立即告警的級別 | `["critical"]` |
| `notification.daily` | 每日審計通知目標 | `"<your-notification-target>"` |
| `notification.weekly` | 每週審計通知目標 | `"<your-notification-target>"` |
| `notification.monthly` | 每月審計通知目標 | `"<your-notification-target>"` |

`retention` 對應 4.3 的清理策略，`severity` 對應 4.1 的嚴重度分級，`audit_schedule` 對應 3.2 的審計週期。`notification` 配置各審計級別的通知頻道（郵件、IM、webhook 等），格式取決於你的通知系統。

## 5. 實踐指南

### 5.1 如何應用

**第一步：定義你的記憶層級**

不一定需要五層。關鍵原則：

- 每層有明確的職責邊界（什麼資訊屬於哪層）
- 每層有容量限制（防止無限膨脹）
- 層級之間有清晰的流轉規則（什麼時候從 Memory 升級到 Skills）

**第二步：建立審計機制**

根據你的排程能力選擇頻率：

| 頻率 | 適合場景 |
|------|----------|
| 每日 | 記憶頻繁更新的 Agent |
| 每週 | 中等使用頻率 |
| 每月 | 低頻或輔助審計 |

**第三步：實現反饋迴圈**

使用回饋狀態檔（推薦 JSON 格式）追蹤活躍項目。報告保留歷史，狀態檔只儲存當前。

信封結構：
- `version`：Schema 版本（整數，如 `1`）
- `updated`：最後修改時間（ISO-8601）
- `items`：回饋條目陣列

每條核心欄位：
- `id`：唯一識別
- `issue`：問題描述
- `severity`：嚴重度級別（trivial / minor / moderate / major / critical）
- `action`：建議操作
- `status`：當前狀態（pending / decided / deferred）
- `created`：發現時間（ISO-8601）
- `decision`：使用者決策文字（decided/deferred 時填寫）
- `decided`：決策時間（decided 時填寫）

**第四步：配置清理策略**

設定保留期限：
- 每日報告：7-30 天
- 每週/月報告：永久
- 反饋逾時：30-90 天

### 5.2 適配建議

| 你的場景 | 建議 |
|----------|------|
| 單 Agent，檔案儲存 | 直接採用本架構 |
| 多 Agent，共享記憶 | 新增共享知識層，審計時合併視圖 |
| 資料庫儲存 | 反饋狀態用資料庫表，報告用結構化記錄 |
| 無定時排程 | 手動觸發審計，或在會話開始時檢查 |
| 無通知頻道 | 審計結果寫入日誌，會話時展示 |

### 5.3 常見陷阱

**審計判斷標準不明確**

最容易犯的錯誤是把條目放錯層級。明確分類規則：

- Profile 只放互動偏好（溝通風格、語言、審批模式）
- Memory 只放短事實和行為約束（一行索引）
- Skills 放完整流程和深度知識

如果一條資訊既有偏好又有流程，拆成兩部分分別存放。

**審計執行者的上下文限制**

如果審計由 AI Agent 自身執行（而非獨立腳本），需要注意一個根本性矛盾：審計者無法同時擁有被審計記憶的完整視圖和獨立判斷力。

- Agent 的工具可能無法讀取自身記憶的全部內容
- Agent 的判斷可能受自身記憶中的偏見影響
- 解決方案：使用預執行腳本將當前狀態注入審計上下文，或定期用獨立腳本交叉驗證

> 以 Hermes Agent 為例：cron 審計任務以 `skip_memory` 模式執行，無法直接呼叫 memory 工具。透過預執行腳本（pre-exec script）將當前記憶狀態序列化後注入上下文，繞過這一限制。

**反饋逾時設定過短**

60 天是推薦值。如果你的使用者不經常上線，考慮延長到 90 天或更長。逾時刪除是兜底機制，不應頻繁觸發。

**備份與清理的時機**

清理前必須備份。建議流程：
1. 審計前建立備份
2. 執行審計，產生報告
3. 自動處理 trivial/minor
4. 報告 moderate/major 給使用者
5. 使用者確認後再刪除備份

### 5.4 常見問題

**Q: 審計會不會很慢？**

A: 每日審計只檢查明顯問題（容量、重複），通常幾秒完成。深度審查留給每週/月。

**Q: 使用者不回覆怎麼辦？**

A: pending 項保持，不推送提醒。超過 60 天自動清理。使用者永遠可以主動查看待決項。

**Q: 如何處理誤刪？**

A: 每次審計前備份。週/月報告永久保留，可從中恢復決策記錄。

**Q: 可以只做部分審計嗎？**

A: 可以。三級是建議，你可以只做每日（輕量）或只做每月（深度）。

## 附錄：設計決策記錄

| 決策 | 考慮的替代方案 | 選擇理由 |
|------|----------------|----------|
| 報告即歷史 | 獨立決策資料庫 | 更簡單，報告已包含完整上下文 |
| 檔案系統儲存 | 資料庫/向量儲存 | 人類可讀、可版本控制、無基礎設施依賴 |
| 手動分類 | 自動嵌入路由 | 確定性、可解釋、無模型依賴 |
| 固定保留期 | 動態調整 | 簡單可預測，不增加複雜度 |
| 60 天逾時 | 無逾時 | 防止殭屍條目，強制週期性決策 |
| 三級審計 | 單級或多級 | 三級互補，每級獨立可選 |
| 反饋追蹤在審計側 | 反饋追蹤在記憶側 | 審計系統負責品質，記憶系統負責儲存 |
