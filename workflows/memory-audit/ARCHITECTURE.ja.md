# Memory Audit アーキテクチャ

> AI Agent の永続メモリ管理のためのアーキテクチャ設計です。

---

## 1. 問題

AI Agent のメモリは時間とともに劣化します。

各セッションで新しい情報が生成されます——ユーザーの好み、環境事実、操作の経験などです。これらの情報は永続ストレージに書き込まれ、セッション間で保持されます。しかし、それらをクリーンアップするメカニズムはありません。

結果は予測可能です：

- **冗長性**：同じ情報が異なる形式で複数のレイヤに存在する
- **陳腐化**：環境の変化後、古いエントリが正確でなくなる
- **膨張**：メモリ容量が徐々に消費され、新しい情報の圧縮スペースが減少する
- **混乱**：エントリの分類ミス、好みとプロセスが混在する

これはストレージ容量の問題ではなく、情報品質の問題です。古く冗長なエントリで満たされたメモリシステムは、メモリがない場合よりも危険です——Agent が誤った前提に基づいて判断を行うためです。

Memory Audit は能動的な管理メカニズムです。定期的な監査、段階的な応答、フィードバックの追跡により、メモリの正確さと可用性を維持します。

## 2. コア理念

### 2.1 能動的は受動的より優れている

> メモリが溢れてからクリーンアップするのではなく、事前に行う。

定期的な監査は問題の蓄積を防ぎ、危機への対応ではありません。定期的な健康診断が緊急治療より効果的であるのと同じです——早期発見された問題は修復しやすく、コストも低くなります。

**実践**：3段階の監査サイクル（毎日/毎週/毎月）、軽量スキャンから深度レビューまで。

### 2.2 レポートは歴史である

> 監査レポートそのものが判断記録である。

別の判断ストレージは不要です。各レポートには当期のレビュー結果、発見された問題、実施されたアクション、ユーザーの判断が含まれます。歴史はレポートの中に書かれています。

**実践**：フィードバック状態ファイルはアクティブな項目（pending/deferred）のみを追跡し、完了した判断はレポートにアーカイブされた後に削除されます。

### 2.3 段階的な応答

> すべての問題に人間の介入が必要なわけではない。

重要度が応答パスを決定します。フォーマットの問題は自動修復され、分類ミスには手動の判断が必要です。これにより、ユーザーは本当に重要な判断のみに集中でき、些細なことに煩わされません。

**実践**：5段階の重要度（trivial → critical）、自動修復から即時アラートまで。

### 2.4 ユーザー操作の最小化

> 一度の応答ですべての保留項目を処理する。

ユーザーが1件ずつ承認する必要はありません。バッチ操作を提供します：「すべて承認」「すべて無視」「延期」、あるいは1回のカスタム指示で複数のエントリを処理します。

**実践**：インタラクションプロトコルはバッチ操作をサポートし、応答がない場合はpending状態のまま、リマインダーのプッシュはありません。

## 3. 概念モデル

### 3.1 メモリモデル

監査システムは監査対象を理解する必要があります。AI Agent の永続メモリは通常、安定性と用途によってレイヤ分けされます：

```
┌─────────────────────────────────────────────────────┐
│  Layer 1: Config                                     │
│  プラットフォーム認証情報、サービス設定、機能フラグ          │
│  変化頻度：極めて少ない                               │
├─────────────────────────────────────────────────────┤
│  Layer 2: Profile                                    │
│  インタラクションの好み、コミュニケーションスタイル、ユーザーの習慣 │
│  変化頻度：時折                                       │
├─────────────────────────────────────────────────────┤
│  Layer 3: Memory                                     │
│  1行インデックス、Skills の詳細コンテンツを参照          │
│  変化頻度：中程度                                     │
├─────────────────────────────────────────────────────┤
│  Layer 4: Skills                                     │
│  完全なワークフロー、詳細マニュアル、深度知識            │
│  変化頻度：中程度                                     │
├─────────────────────────────────────────────────────┤
│  Layer 5: Session                                    │
│  現在の会話コンテキスト、一時的な状態                   │
│  変化頻度：非常に高い（セッション単位）                │
└─────────────────────────────────────────────────────┘
```

**設計意図**：

- **Progressive Disclosure**：Memory は1行インデックスのみを保存し、Skills が完全なコンテンツを保存します。これにより、Agent のアクティブコンテキストは簡潔に保たれ、必要な時にのみ詳細を読み込みます。
- **Separation of Concerns**：設定、好み、知識、コンテキストはそれぞれの場所に分離され、互いに汚染されません。

**保存判断**：

```
情報 X を永続化する必要がある
    │
    ├─ プラットフォーム設定/認証情報？  → Config (Layer 1)
    ├─ インタラクションに影響する好み？ → Profile (Layer 2)
    ├─ 短い事実/行動制約？            → Memory (Layer 3)
    ├─ 再利用可能なワークフロー/深度知識？→ Skills (Layer 4)
    └─ 現在のセッションのみ関連？     → Session (Layer 5)、永続化しない
```

> 5レイヤは参考モデルであり、厳格な要件ではありません。シンプルな Agent は3レイヤ（Config / Memory / Session）だけかもしれません。監査システムはあなたの実際のレイヤ構造に適応すべきです。

### 3.2 監査サイクル

3段階の監査が異なる深度をカバーします：

```
┌─────────────────────────────────────────────────────┐
│  毎日監査                                            │
│  軽量スキャン：容量チェック、重複検出、フォーマットの問題   │
│  trivial/minor を自動処理、moderate/major を記録     │
├─────────────────────────────────────────────────────┤
│  毎週監査                                            │
│  中程度のレビュー：7日間の発見をまとめ、個別に深度チェック │
│  フィードバックの処理、クリーンアップの実行、週次レポートの生成 │
├─────────────────────────────────────────────────────┤
│  毎月監査                                            │
│  深度レビュー：週間のトレンド、ヘルススコア、長期分析     │
│  月次データの集計、遺留問題の追跡                      │
└─────────────────────────────────────────────────────┘
```

**なぜ3段階なのか？**

- 単一の監査では、頻度が高すぎる（深度監査を毎日実行するのは重すぎる）か、低すぎる（軽量監査を毎月実行するには遅すぎる）のいずれかです
- 3段階が補完し合います：毎日は明白な問題を捕らえ、毎週は判断が必要な問題を処理し、毎月はトレンドを確認します
- 各段階は独立して選択可能です——毎日（軽量）のみ、または毎月（深度）のみも可能です

**設計意図**：

- 毎日監査は高速、自動、ユーザーインタラクションなし
- 毎週監査はユーザーのフィードバックを処理し、主要なインタラクションノードです
- 毎月監査は全体的な視点を提供し、クリーンアップは実行しません

## 4. 主要メカニズム

### 4.1 重要度分類

問題は影響度に応じて5段階に分類されます：

| レベル | 定義 | 応答 |
|--------|------|------|
| **trivial** | 可読性のみに影響（フォーマット、句読点） | 自動修復、記録なし |
| **minor** | 改善のための修正、意味は変わらない | 自動修復、レポートに記録 |
| **moderate** | エントリの移動または書き直しが必要 | レポート、ユーザーの承認待ち |
| **major** | 削除または大幅な書き直しが必要 | レポート、ユーザーの承認待ち |
| **critical** | セキュリティまたはデータ整合性に関わる | 即時アラート + 自動修復 |

**設計意図**：

- trivial/minor が大多数を占め、自動処理で時間を節約
- moderate/major は判断が必要で、ユーザーに委ねる
- critical は稀だが緊急、即座に対応

### 4.2 フィードバックライフサイクル

監査で発見された問題はフィードバック追跡システムに入り、完全なライフサイクルを経験します：

```
    ┌──────────┐
    │  監査    │
    │  発見    │
    └────┬─────┘
         │
         ▼
    ┌──────────┐
    │  pending │ ← 新しい問題が入る
    └────┬─────┘
         │
    ┌────┴────┐
    ▼         ▼
┌────────┐ ┌──────────┐
│decided │ │ deferred │
│(判断済み)│ │ (延期)   │
└────┬───┘ └────┬─────┘
     │          │
     ▼          ▼
┌──────────┐ ┌──────────┐
│ 次の     │ │ 判断まで  │
│ レポート │ │ または   │
│ アーカイブ│ │ タイムアウト│
└──────────┘ └──────────┘
```

**状態の説明**：

- **pending**：新しく発見された問題、ユーザーの処理待ち
- **decided**：ユーザーが判断を下した（承認/無視）
- **deferred**：ユーザーが延期し、後で処理

**クリーンアップルール**：

- decided の項目は次のレポートに表示された後に削除されます
- すべての項目は60日後に自動削除されます（フェイルセーフメカニズム）
- deferred の項目はユーザーの判断または60日間保持されます

**なぜデータベースではなくファイルなのか？**

- 人間が読める：feedback.json を直接開いて状態を確認可能
- バージョン管理可能：git diff で変更を追跡
- インフラ依存なし：データベースサービスの実行が不要
- 十分にシンプル：フィードバックエントリは通常1桁から低2桁程度

**設計意図**：

- レポートそのものが履歴であり、追加のストレージは不要
- 60日間のタイムアウトで停滞エントリの蓄積を防止
- ユーザーが応答しない場合、pending 状態のまま、リマインダーのプッシュなし

### 4.3 スマートクリーンアップ

ファイルのクリーンアップは保留状態に応じて決定されます：

```
pending がなく、moderate/major の問題もない
    → 期限切れファイルを自動削除

trivial/minor の問題のみ
    → 自動削除

moderate/major の pending あり
    → ユーザーの確認後に削除
```

**設計意図**：

- 保留項目がない場合、クリーンアップは安全で自動実行される
- 保留項目がある場合、ユーザーの参照用にファイルを保持する
- ユーザーが考えている間に証拠を削除することを避ける

### 4.4 設定構造

監査システムは設定ファイルを通じて動作を制御します。JSON 形式（`config.json`）の使用を推奨し、以下のセクションを含みます：

| フィールド | 説明 | 例 |
|-----------|------|-----|
| `data_dir` | データ保存ルートディレクトリ | `$DATA_DIR/memory-audit` |
| `retention.daily_reports` | 毎日レポートの保持日数 | `14` |
| `retention.daily_backups` | 毎日バックアップの保持日数 | `14` |
| `retention.weekly_reports` | 週次レポートの保持日数（-1 = 永久） | `-1` |
| `retention.monthly_reports` | 月次レポートの保持日数（-1 = 永久） | `-1` |
| `retention.feedback_timeout_days` | フィードバックエントリのタイムアウト日数 | `60` |
| `audit_schedule.daily` | 毎日監査の cron 式 | `0 9 * * *` |
| `audit_schedule.weekly` | 毎週監査の cron 式 | `0 10 * * 1` |
| `audit_schedule.monthly` | 毎月監査の cron 式 | `0 10 1 * *` |
| `severity.auto_fix` | 自動修復対象の重要度レベル | `["trivial", "minor"]` |
| `severity.require_approval` | ユーザー承認が必要なレベル | `["moderate", "major"]` |
| `severity.immediate_alert` | 即時アラート対象のレベル | `["critical"]` |
| `notification.daily` | 毎日監査の通知先 | `"<your-notification-target>"` |
| `notification.weekly` | 毎週監査の通知先 | `"<your-notification-target>"` |
| `notification.monthly` | 毎月監査の通知先 | `"<your-notification-target>"` |

`retention` は4.3のクリーンアップ戦略に対応し、`severity` は4.1の重要度分類に対応し、`audit_schedule` は3.2の監査サイクルに対応します。`notification` は各監査レベルの通知チャネル（メール、IM、webhook など）を設定し、フォーマットはお使いの通知システムに依存します。

## 5. 実践ガイド

### 5.1 適用方法

**ステップ1：メモリレイヤを定義する**

5レイヤである必要はありません。重要な原則：

- 各レイヤに明確な責任境界がある（どの情報がどのレイヤに属するか）
- 各レイヤに容量制限がある（無限の膨張を防ぐ）
- レイヤ間に明確な移行ルールがある（いつ Memory から Skills に昇格するか）

**ステップ2：監査メカニズムを構築する**

スケジューリング能力に応じて頻度を選択してください：

| 频度 | 適したシナリオ |
|------|--------------|
| 毎日 | メモリが頻繁に更新される Agent |
| 毎週 | 中程度の使用頻度 |
| 毎月 | 低頻度または補助監査 |

**ステップ3：フィードバックループを実装する**

フィードバック状態ファイル（JSON 推奨）でアクティブな項目を追跡します。レポートが履歴を保持し、状態ファイルは現在のみを保存します。

主要フィールド：
- `id`：一意識別子
- `issue`：問題の説明
- `severity`：重要度レベル（trivial / minor / moderate / major / critical）
- `action`：推奨アクション
- `status`：現在の状態（pending / decided / deferred）
- `created`：発見日時（ISO-8601）
- `decision`：ユーザーの判断テキスト（decided/deferred 時に記入）
- `decided`：判断日時（decided 時に記入）

**ステップ4：クリーンアップ戦略を設定する**

保持期間を設定してください：
- 毎日レポート：7〜30日
- 毎週/毎月レポート：永久
- フィードバックタイムアウト：30〜90日

### 5.2 適応のアドバイス

| あなたのシナリオ | 推奨 |
|-----------------|------|
| 単一 Agent、ファイルストレージ | 本アーキテクチャをそのまま採用 |
| 複数 Agent、共有メモリ | 共有知識レイヤを追加、監査時にビューを統合 |
| データベースストレージ | フィードバック状態にデータベーステーブル、レポートに構造化レコード |
| 定時スケジューリングなし | 手動で監査をトリガー、またはセッション開始時にチェック |
| 通知チャネルなし | 監査結果をログに書き込み、セッション時に表示 |

### 5.3 よくある落とし穴

**監査判断基準が不明確**

最も犯しやすいミスは、エントリを間違ったレイヤに配置することです。分類ルールを明確にしてください：

- Profile にはインタラクションの好み（コミュニケーションスタイル、言語、承認モード）のみ配置
- Memory には短い事実と行動制約のみ配置（1行インデックス）
- Skills には完全なワークフローと深度知識を配置

1つの情報に好みとワークフローの両方が含まれる場合は、2つの部分に分割してそれぞれ保存してください。

**監査実行者のコンテキスト制限**

監査が AI Agent 自体によって実行される場合（独立したスクリプトではなく）、根本的な矛盾に注意が必要です：監査者は監査対象のメモリの完全なビューと独立した判断力を同時に持つことができません。

- Agent のツールは自身のメモリの全コンテンツを読み取れない場合がある
- Agent の判断は自身のメモリのバイアスに影響される場合がある
- 解決策：実行前スクリプトで現在の状態を監査コンテキストに注入するか、定期的に独立したスクリプトで交差検証する

> Hermes Agent を例に挙げると：cron 監査タスクは `skip_memory` モードで実行され、memory ツールを直接呼び出すことはできません。実行前スクリプト（pre-exec script）で現在のメモリ状態をシリアライズしてコンテキストに注入し、この制限を回避します。

**フィードバックのタイムアウト設定が短すぎる**

60日は推奨値です。ユーザーが頻繁にオンラインにならない場合は、90日以上への延長を検討してください。タイムアウト削除はフェイルセーフメカニズムであり、頻繁にトリガーされるべきではありません。

**バックアップとクリーンアップのタイミング**

クリーンアップ前にバックアップが必須です。推奨ワークフロー：
1. 監査前にバックアップを作成
2. 監査を実行し、レポートを生成
3. trivial/minor を自動処理
4. moderate/major をユーザーに報告
5. ユーザーの確認後にバックアップを削除

### 5.4 よくある質問

**Q: 監査は遅くならないですか？**

A: 毎日監査は明白な問題（容量、重複）のみをチェックし、通常数秒で完了します。深度レビューは毎週/毎月に委ねます。

**Q: ユーザーが応答しない場合はどうなりますか？**

A: pending の項目は保持され、リマインダーのプッシュはありません。60日を過ぎると自動クリーンアップされます。ユーザーはいつでも保留項目を確認できます。

**Q: 誤削除はどう対処しますか？**

A: 各監査前にバックアップを行います。週次/月次レポートは永久に保持され、そこから判断記録を復元できます。

**Q: 部分的な監査のみ実行できますか？**

A: はい。3段階は推奨であり、毎日（軽量）のみ、または毎月（深度）のみでも実行可能です。

## 付録：設計判断記録

| 判断 | 検討した代替案 | 選択理由 |
|------|--------------|---------|
| レポートは歴史である | 独立した判断データベース | よりシンプル、レポートに完全なコンテキストが含まれる |
| ファイルシステムストレージ | データベース/ベクトルストレージ | 人間が読め、バージョン管理可能、インフラ依存なし |
| 手動分類 | 自動埋め込みルーティング | 確定的、説明可能、モデル依存なし |
| 固定保持期間 | 動的調整 | シンプルで予測可能、複雑さを増さない |
| 60日タイムアウト | タイムアウトなし | 停滞エントリを防止、周期的な判断を強制 |
| 3段階監査 | 単一または多段階 | 3段階が補完し合い、各段階が独立して選択可能 |
| フィードバック追跡は監査側 | フィードバック追跡はメモリ側 | 監査システムが品質を担当、メモリシステムがストレージを担当 |
